# テキスト候補型カスタム部門MVP 要件定義書

## 概要

カップル2人が年ごとにテキスト候補型カスタム部門を複数作成し、候補項目とポイント設定を確定したうえで、それぞれ順位付きで投票する。両方の入力が完了するまで相手の入力内容は表示せず、両方完了後に部門ごとのポイント設定に従って集計結果を表示する。

今回のMVPでは、CSV / XLSX読み込み、関連画像添付、Cloud Storage連携は後続フェーズに分離する。まずは手入力候補だけで「部門作成 -> 候補管理 -> 候補・設定確定 -> 順位入力 -> 入力完了 -> 結果発表 -> リセット」の一連の流れを実装可能な仕様にする。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングから妥当な推測による要件
- 🔴 **赤信号**: PRD・EARS要件定義書・設計文書・ユーザヒアリングにない推測による要件

### 通常要件

- REQ-001: システムは、年ごとにテキスト候補型カスタム部門を複数作成できなければならない。🔵 *docs/requirements.md 6.6, 6.11 / ユーザヒアリング2026-06-24*
- REQ-002: システムは、テキスト候補型カスタム部門を年間のみで扱わなければならない。🔵 *docs/requirements.md 6.6*
- REQ-003: システムは、MVPでは候補項目を手入力で追加できなければならない。🔵 *docs/requirements.md 6.6*
- REQ-004: システムは、MVPでは候補項目の候補名を編集できなければならない。🔵 *docs/requirements.md 6.6*
- REQ-005: システムは、候補項目を削除できなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-006: システムは、部門ごとに何位まで入力するかを1位から50位までの範囲で設定できなければならない。🔵 *docs/requirements.md 6.6, 6.11 / ユーザヒアリング2026-06-24*
- REQ-007: システムは、部門ごとに何位までを結果発表対象に含めるかを1位から50位までの範囲で設定できなければならない。🔵 *docs/requirements.md 6.6, 6.11 / ユーザヒアリング2026-06-24*
- REQ-008: システムは、部門ごとに順位別ポイントを最大50行まで設定できなければならない。🔵 *docs/requirements.md 6.6, 6.11 / ユーザヒアリング2026-06-24*
- REQ-009: システムは、ユーザーがテキスト候補型カスタム部門で順位付きのベストを選べるようにしなければならない。🔵 *docs/requirements.md 6.6*
- REQ-010: システムは、テキスト候補型カスタム部門の入力を自分と相手でそれぞれ保持しなければならない。🔵 *docs/requirements.md 6.6*
- REQ-011: システムは、部門ごとのポイント設定に従って2人分の順位入力を集計できなければならない。🔵 *docs/requirements.md 6.6, 8*
- REQ-012: システムは、集計結果を発表対象順位まで表示できなければならない。🔵 *docs/requirements.md 6.6, 8*
- REQ-013: システムは、対象部門を全体リセットできなければならない。🔵 *docs/requirements.md 6.6*
- REQ-014: システムは、リセット後に候補と部門設定を残したまま確定前状態へ戻し、再確定後に2人が再入力できる状態へ戻さなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-015: システムは、リセットなしで結果発表を再表示できなければならない。🔵 *docs/requirements.md 9*
- REQ-016: システムは、1年あたり最大30件程度のテキスト候補型カスタム部門を扱える前提で設計しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-017: システムは、MVPでは関連画像の保存・選択を行わないが、候補項目の表示・編集UIに関連画像枠を用意しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-018: システムは、1部門あたり最大100件の候補項目を扱える前提で設計しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-019: システムは、候補項目、入力対象順位、発表対象順位、順位別ポイントを確定できなければならない。🔵 *ユーザヒアリング2026-06-24*

### 条件付き要件

- REQ-101: 候補項目が入力順位数より少ない場合、システムは不足していることをユーザーに示し、入力完了を許可してはならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-102: ユーザーが入力完了する場合、システムは同じ候補が複数順位に選ばれていないことを検証しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-103: 自分だけが入力完了している場合、システムは相手の入力内容と集計結果を表示してはならない。🔵 *docs/requirements.md 6.3, 6.6*
- REQ-104: 両方のユーザーが入力完了している場合、システムは集計結果を表示できなければならない。🔵 *docs/requirements.md 6.3, 6.6, 8*
- REQ-105: ユーザーが部門リセットを実行する場合、システムは対象部門全体のリセットであることを示す確認ダイアログを表示しなければならない。🔵 *docs/requirements.md 6.6*
- REQ-106: リセットが確定した場合、システムは対象部門の2人分の順位入力、入力状態、生成済み結果を削除し、候補と部門設定を残したまま確定前状態へ戻さなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-107: 候補項目を追加する場合、システムはFirestore上のトランザクションまたは同等の排他制御により、同時追加を失わずに保存しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-108: システムは、同一部門内に同名の候補項目が複数存在することを許容しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-109: 候補項目と部門設定が未確定の場合、システムはどちらのユーザーにも順位入力を許可してはならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-110: 候補項目と部門設定が確定済みの場合、システムは候補追加、候補編集、候補削除、入力対象順位、発表対象順位、ポイント設定の変更を制限しなければならない。🔵 *ユーザヒアリング2026-06-24*

### 状態要件

- REQ-201: 部門が未作成の状態にある場合、システムは年を選んで新しいテキスト候補型カスタム部門を作成する導線を表示しなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-202: 候補・設定が未確定の状態にある場合、システムは候補の追加、編集、削除、入力対象順位、発表対象順位、順位別ポイントの編集を可能にしなければならない。🔵 *docs/requirements.md 6.6 / ユーザヒアリング2026-06-24*
- REQ-203: 候補・設定が確定済みで入力中の状態にある場合、システムは選択済み順位と未選択順位を確認できるようにしなければならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-204: 自分の入力が完了して相手が未完了の状態にある場合、システムは相手の入力状況だけを表示し、相手の選択内容を表示してはならない。🔵 *docs/requirements.md 6.3*
- REQ-205: 両方の入力が完了した状態にある場合、システムはポイント集計結果を表示しなければならない。🔵 *docs/requirements.md 6.6, 8*

### オプション要件

- REQ-301: システムは、後続フェーズでCSV / XLSXファイルから候補名を読み込めてもよい。🔵 *docs/requirements.md 6.6, 9*
- REQ-302: システムは、後続フェーズで候補項目に1枚の関連画像を添付できてもよい。🔵 *docs/requirements.md 6.6, 9*
- REQ-303: システムは、結果発表画面で下位から上位へ期待感が高まる演出を提供してもよい。🔵 *docs/requirements.md 6.3*

### 制約要件

- REQ-401: システムは、テキスト候補型カスタム部門MVPのデータをCloud Firestoreで管理しなければならない。🔵 *docs/requirements.md 6.10*
- REQ-402: システムは、Firebase Anonymous Authenticationで識別されたユーザーを前提に、自分の入力だけを編集可能にしなければならない。🔵 *docs/requirements.md 6.6, 6.10*
- REQ-403: システムは、相手のテキスト候補型カスタム部門入力を編集できないようにしなければならない。🔵 *docs/requirements.md 6.6*
- REQ-404: システムは、2人のユーザー間で入力状況と結果を同期しなければならない。🔵 *docs/requirements.md 6.10*
- REQ-405: システムは、結果発表の公開条件をクライアント表示制御だけでなくFirestore Security Rulesでも保護する前提で設計しなければならない。🔵 *docs/tech-stack.md*
- REQ-406: システムは、ペアコード、ユーザーID、候補内容など個人情報になり得る値を不要にログ出力してはならない。🔵 *AGENTS.md / docs/tech-stack.md*
- REQ-407: システムは、MVPでは候補関連画像の選択・保存・Cloud Storage書き込みを行ってはならない。🔵 *ユーザヒアリング2026-06-24*
- REQ-408: システムは、関連画像の後続実装を見越し、候補編集画面、候補一覧、結果表示で画像枠またはプレースホルダーを表示できなければならない。🔵 *ユーザヒアリング2026-06-24*

## 非機能要件

- NFR-001: 1年あたり30部門程度、1部門あたり候補100件、入力対象順位・発表対象順位・ポイント設定行数50件を扱っても、部門一覧、候補一覧、順位入力画面、結果画面の操作性が大きく低下しないようにする。🔵 *ユーザヒアリング2026-06-24*
- NFR-002: ポイント集計はクライアント表示時に即時確認できる計算量に収める。🔵 *ユーザヒアリング2026-06-24*

### セキュリティ・プライバシー

- NFR-101: ペアに属する2人以外は、対象年の部門、候補、入力状態、結果にアクセスできない。🔵 *docs/requirements.md 6.10 / docs/tech-stack.md*
- NFR-102: 両方完了前の相手入力と集計結果は、画面表示とFirestore Rulesの両方で保護する。🔵 *docs/requirements.md 6.3 / docs/tech-stack.md*
- NFR-103: 削除やリセットなど誤操作の影響が大きい操作には確認手段を用意する。🔵 *docs/requirements.md 7.4*

### ユーザビリティ

- NFR-201: 主要操作はiPhone片手操作でも理解しやすいSwiftUI標準パターンで提供する。🔵 *AGENTS.md / docs/tech-stack.md*
- NFR-202: 入力順位、候補、入力状態、結果順位は視覚的に区別しやすく表示する。🔵 *docs/requirements.md 7.4*
- NFR-203: Dynamic Type、十分なコントラスト、44pt以上のタップ領域を意識する。🔵 *ユーザヒアリング2026-06-24*

## Edgeケース

### エラー処理

- EDGE-001: Firestoreへの保存に失敗した場合、システムはユーザーに保存できなかったことを示し、入力中の内容を可能な限り保持する。🔵 *docs/requirements.md 7.2*
- EDGE-002: リセットに失敗した場合、システムは部門データを中途半端に消したように見せず、現在の状態を再取得できるようにする。🔵 *ユーザヒアリング2026-06-24*
- EDGE-003: 候補・設定が確定済みの場合、システムは既存入力との整合性を保つため、候補変更と部門設定変更を制限しなければならない。🔵 *ユーザヒアリング2026-06-24*

### 境界値

- EDGE-101: 入力対象順位が1位までの場合も、順位入力、完了、集計、結果表示が成立する。🔵 *ユーザヒアリング2026-06-24*
- EDGE-102: 発表対象順位が入力対象順位より大きい設定は保存できない。🔵 *ユーザヒアリング2026-06-24*
- EDGE-103: 順位別ポイントに0点以下は設定できない。🔵 *ユーザヒアリング2026-06-24*

## MVP対象外

- CSV / XLSXファイルからの候補読み込み。🔵 *後続分離*
- 関連画像の選択、保存、アップロード。🔵 *後続分離*
- 関連画像のCloud Storage保存、削除、表示。🔵 *後続分離*
- 月間ベスト、年間ベスト、メディア型カスタム部門、敗者復活枠。🔵 *ユーザー指定スコープ外*

## 品質判定

- 要件の曖昧さ: MVP範囲は明確。部門数上限は1年あたり30部門程度、候補数上限は1部門あたり100件、入力対象順位・発表対象順位・ポイント設定行数は50件として確認済み。
- 入出力定義: 部門、候補、候補・設定確定状態、順位入力、入力状態、集計結果は定義済み。FirestoreパスとSwift型は設計フェーズで具体化する。
- 制約条件: iOS / SwiftUI / Firebase / 過去生成物非参照 / 環境構築済み前提を明記済み。
- 実装可能性: 高い。Storageやファイル読み込みを後続化したため、MVPとして実装可能。
- 信頼性レベル: すべての要件項目が🔵。未決定事項は要件の信頼性ではなく、設計フェーズで具体化する実装方式として扱う。
