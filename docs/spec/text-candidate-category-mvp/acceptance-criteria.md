## REQ-001〜REQ-008, REQ-019: 部門作成・設定・確定 🔵

**信頼性**: 🔵 *docs/requirements.md 6.6, 6.11*

### Given（前提条件）

- ユーザーはペアに参加済みである。
- 対象年が選択されている。

### When（実行条件）

- ユーザーがテキスト候補型カスタム部門を作成する。

### Then（期待結果）

- 部門名、対象年、入力対象順位、発表対象順位、順位別ポイントが保存される。
- 作成した部門は対象年の部門一覧に表示される。
- 発表対象順位が入力対象順位を超える設定は保存できない。
- 入力対象順位、発表対象順位、順位別ポイントは最大50件まで設定できる。
- 候補項目と部門設定を確定できる。
- 1年あたり30部門程度を扱える前提で、部門一覧が破綻しない。

### テストケース

#### 正常系

- [ ] **TC-001-01**: 部門を作成できる 🔵
  - **入力**: 年、部門名、入力対象順位、発表対象順位、順位別ポイント
  - **期待結果**: 部門が保存され一覧に表示される
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

- [ ] **TC-001-02**: 部門ごとに順位別ポイントを保存できる 🔵
  - **入力**: 1位10pt、2位5pt、3位3pt
  - **期待結果**: 部門設定として保存される
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

- [ ] **TC-001-03**: 年ごとに複数部門を作成できる 🔵
  - **入力**: 同一年に30件程度の部門
  - **期待結果**: 部門一覧で対象年の複数部門を確認できる
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

- [ ] **TC-001-04**: 候補と部門設定を確定できる 🔵
  - **入力**: 入力対象順位以上の候補、入力対象順位、発表対象順位、順位別ポイント
  - **期待結果**: 部門が確定済みになり、順位入力へ進める
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

#### 異常系

- [ ] **TC-001-E01**: 部門名が空の場合は保存できない 🔵
  - **入力**: 空の部門名
  - **期待結果**: ユーザーに入力不足が示される
  - **信頼性**: 🔵 *部門作成要件から必須入力として整理*

#### 境界値

- [ ] **TC-001-B01**: 入力対象順位が1位まででも作成できる 🔵
  - **入力**: 入力対象順位1、発表対象順位1
  - **期待結果**: 部門が保存される
  - **信頼性**: 🔵 *EDGE-101 / ユーザヒアリング2026-06-24*

- [ ] **TC-001-B02**: 0点以下の順位別ポイントは保存できない 🔵
  - **入力**: 1位0pt
  - **期待結果**: 1以上のポイント入力を促す
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

## REQ-003〜REQ-005: 候補項目の手入力管理 🔵

**信頼性**: 🔵 *docs/requirements.md 6.6*

### Given（前提条件）

- テキスト候補型カスタム部門が存在する。

### When（実行条件）

- ユーザーが候補項目を追加、編集、削除する。

### Then（期待結果）

- 候補名が保存される。
- 候補名を編集できる。
- 不要な候補を削除できる。
- 1部門あたり最大100件の候補を扱える。
- 候補・設定が確定済みの場合、候補の追加、編集、削除はできない。
- MVPではCSV / XLSX読み込み、関連画像の選択・保存・アップロードは行わない。
- 候補一覧と候補編集UIには関連画像枠またはプレースホルダーが表示される。

### テストケース

#### 正常系

- [ ] **TC-003-01**: 候補を手入力で追加できる 🔵
  - **入力**: 候補名「初日の出を見に行った」
  - **期待結果**: 候補一覧に追加される
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

- [ ] **TC-003-02**: 候補名を編集できる 🔵
  - **入力**: 既存候補名の変更
  - **期待結果**: 更新後の候補名が表示される
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

- [ ] **TC-003-03**: 候補UIに関連画像枠を表示できる 🔵
  - **入力**: 候補名のみ
  - **期待結果**: 画像未設定のプレースホルダーが表示され、画像選択・保存は実行されない
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

#### 異常系

- [ ] **TC-003-E01**: 空の候補名は追加できない 🔵
  - **入力**: 空文字
  - **期待結果**: 候補名の入力を促す
  - **信頼性**: 🔵 *候補手入力要件から必須入力として整理*

- [ ] **TC-003-04**: 同一部門内で同名候補を追加できる 🔵
  - **入力**: 同じ候補名を複数回追加
  - **期待結果**: 同名でも別候補として保存される
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

## REQ-009〜REQ-010: 自分の順位入力 🔵

**信頼性**: 🔵 *docs/requirements.md 6.6*

### Given（前提条件）

- テキスト候補型カスタム部門が存在する。
- 候補項目、入力対象順位、発表対象順位、順位別ポイントが確定済みである。
- 入力対象順位以上の候補が存在する。

### When（実行条件）

- ユーザーが候補から順位付きでベストを選び、入力完了する。

### Then（期待結果）

- 自分の順位入力が保存される。
- 同じ候補を複数順位に選択できない。
- 入力完了状態が保存される。
- 相手の入力は編集できない。

### テストケース

#### 正常系

- [ ] **TC-009-01**: 順位付き入力を完了できる 🔵
  - **入力**: 1位候補A、2位候補B、3位候補C
  - **期待結果**: 自分の入力として保存される
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

- [ ] **TC-009-02**: 候補・設定が未確定の場合は順位入力できない 🔵
  - **入力**: 未確定の部門で順位入力を開く
  - **期待結果**: 順位入力は開始できず、候補・設定の確定が必要であることが示される
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

#### 異常系

- [ ] **TC-009-E01**: 同じ候補を複数順位に選べない 🔵
  - **入力**: 1位候補A、2位候補A
  - **期待結果**: 重複選択として完了できない
  - **信頼性**: 🔵 *REQ-102 / ユーザヒアリング2026-06-24*

- [ ] **TC-009-E02**: 候補数が入力順位数未満の場合は完了できない 🔵
  - **入力**: 入力対象順位3、候補2件
  - **期待結果**: 候補不足が示される
  - **信頼性**: 🔵 *REQ-101 / ユーザヒアリング2026-06-24*

## REQ-103〜REQ-105: 公開条件と結果表示 🔵

**信頼性**: 🔵 *docs/requirements.md 6.3, 6.6, 8*

### Given（前提条件）

- 自分と相手が同じペアに参加している。
- テキスト候補型カスタム部門が存在する。

### When（実行条件）

- 自分だけ、または両方のユーザーが入力完了する。

### Then（期待結果）

- 片方だけが入力完了している間、相手の入力内容と集計結果は表示されない。
- 両方が入力完了した場合、ポイント設定に従って集計結果が表示される。
- 集計結果は発表対象順位まで表示される。

### テストケース

#### 正常系

- [ ] **TC-103-01**: 片方完了時は相手の結果を表示しない 🔵
  - **入力**: userA完了、userB未完了
  - **期待結果**: userBにはuserAの入力内容が表示されない
  - **信頼性**: 🔵 *docs/requirements.md 6.3*

- [ ] **TC-103-02**: 両方完了時にポイント集計を表示する 🔵
  - **入力**: userA/userBの順位入力、順位別ポイント
  - **期待結果**: 候補ごとの合計点と順位が表示される
  - **信頼性**: 🔵 *docs/requirements.md 6.6, 8*

#### 境界値

- [ ] **TC-103-B01**: 同点候補がある場合も一覧表示が破綻しない 🔵
  - **入力**: 候補Aと候補Bが同点
  - **期待結果**: 同点として一貫した順序で表示される
  - **信頼性**: 🔵 *集計表示要件 / NFR-202*

## REQ-013〜REQ-014: 部門リセット 🔵

**信頼性**: 🔵 *docs/requirements.md 6.6*

### Given（前提条件）

- テキスト候補型カスタム部門が存在する。
- 入力状態または結果が存在する。

### When（実行条件）

- ユーザーが部門リセットを実行し、確認ダイアログで確定する。

### Then（期待結果）

- 対象部門全体のリセットであることが確認される。
- 2人分の入力状態、順位入力、集計結果が削除される。
- 候補と部門設定は残り、確定前状態へ戻る。

### テストケース

#### 正常系

- [ ] **TC-013-01**: リセット確認後に再入力可能になる 🔵
  - **入力**: リセット確定
  - **期待結果**: 入力状態が未入力に戻り、候補・設定は確定前状態へ戻る
  - **信頼性**: 🔵 *docs/requirements.md 6.6*

#### 異常系

- [ ] **TC-013-E01**: リセットをキャンセルした場合は状態が変わらない 🔵
  - **入力**: 確認ダイアログでキャンセル
  - **期待結果**: 入力状態と結果が維持される
  - **信頼性**: 🔵 *確認ダイアログ要件*

- [ ] **TC-EDGE-001**: 保存失敗時に入力内容を可能な限り保持する 🔵

  - **信頼性**: 🔵 *docs/requirements.md 7.2*

  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

- [ ] **TC-EDGE-004**: 2人が同時に別候補を追加しても失われない 🔵
  - **条件**: 2端末が同じ部門に異なる候補名を同時追加する
  - **期待結果**: 両方の候補が保存される
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*

- [ ] **TC-EDGE-005**: 2人が同時に同名候補を追加した場合も両方保存される 🔵
  - **条件**: 2端末が正規化後に同じ候補名を同時追加する
  - **期待結果**: 両方が別候補として保存される
  - **信頼性**: 🔵 *ユーザヒアリング2026-06-24*
